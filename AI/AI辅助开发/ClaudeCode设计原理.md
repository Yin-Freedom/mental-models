# Claude Code 多步骤任务与上下文管理设计原理

## 一、Claude Code vs 直接将需求给大模型

### 核心区别

| 维度 | Claude Code | 直接给大模型 |
|------|-------------|--------------|
| **执行能力** | 可直接操作文件系统、运行命令 | 仅生成文本，需手动执行 |
| **上下文深度** | 可探索整个代码库，理解架构 | 依赖用户提供的上下文 |
| **迭代方式** | 多轮交互，自动迭代完善 | 一锤子买卖，手动迭代 |
| **反馈闭环** | 可运行测试、验证结果 | 无法验证，只能猜测 |
| **错误处理** | 可自动诊断和修复 | 需要用户反馈错误再重新生成 |

### Claude Code 的独特优势

1. **工具链完整**
   - 读写文件 (Read/Write/Edit)
   - 搜索代码 (Glob/Grep)
   - 执行命令 (Bash)
   - 网络搜索/获取 (WebSearch/WebFetch)

2. **探索能力**
   - 可以先探索代码库理解现有架构
   - 找到可复用的模式和组件
   - 理解项目约定和风格

3. **验证能力**
   - 运行测试验证修改
   - 执行代码检查错误
   - 查看实际运行结果

4. **迭代能力**
   - 发现问题可以立即修复
   - 多轮优化直到满意
   - 跟踪复杂任务进度

5. **上下文持久**
   - 记忆文件 (MEMORY.md)
   - 对话历史
   - 项目理解

### 适用场景对比

**Claude Code 适合：**
- 复杂的代码修改任务
- 需要理解现有代码的场景
- 多文件、多步骤的任务
- 需要验证和迭代的工作

**直接给大模型适合：**
- 简单的代码片段生成
- 概念解释和学习
- 不依赖具体代码环境的问答

## 二、多步骤任务执行机制

### 1. 核心架构：Agent 系统

```
┌─────────────────────────────────────────────────────────┐
│                    主对话线程                            │
│  ┌─────────────────────────────────────────────────┐   │
│  │              任务分解与调度                       │   │
│  └─────────────────────────────────────────────────┘   │
│                         │                              │
│         ┌───────────────┼───────────────┐             │
│         ▼               ▼               ▼             │
│    ┌─────────┐    ┌─────────┐    ┌─────────┐          │
│    │ Agent 1 │    │ Agent 2 │    │ Agent 3 │          │
│    │ (探索)  │    │ (规划)  │    │ (通用)  │          │
│    └─────────┘    └─────────┘    └─────────┘          │
│         │               │               │              │
│         └───────────────┴───────────────┘             │
│                         ▼                              │
│                   结果汇总返回                          │
└─────────────────────────────────────────────────────────┘
```

**设计要点：**

| 特性 | 实现方式 | 作用 |
|------|----------|------|
| **并行执行** | 单条消息发起多个 Agent 调用 | 提高效率，独立任务同时处理 |
| **隔离执行** | `isolation: "worktree"` | 防止冲突，创建临时工作区 |
| **后台运行** | `run_in_background: true` | 长任务不阻塞主流程 |
| **上下文继承** | Agent 可访问主对话历史 | 子任务理解全局意图 |

### 2. Agent 类型分工

```yaml
Explore Agent:
  用途: 快速探索代码库
  特点: 只读操作，不修改文件
  场景: 搜索文件、查找模式、理解架构
  工具: All tools except Agent, ExitPlanMode, Edit, Write, NotebookEdit

Plan Agent:
  用途: 设计实现方案
  特点: 架构视角，权衡取舍
  场景: 复杂功能的实现规划
  工具: All tools except Agent, ExitPlanMode, Edit, Write, NotebookEdit

General-purpose Agent:
  用途: 通用多步骤任务
  特点: 全工具访问权限
  场景: 执行具体实现、修复问题
  工具: * (全部工具)
```

### 3. 任务状态管理

```
Task 状态流转：
pending → in_progress → completed
              ↓
           deleted (取消)
              ↓
           blocked (等待依赖)
```

**依赖管理机制：**
- `blockedBy`: 该任务依赖哪些任务
- `blocks`: 哪些任务依赖该任务
- 形成任务依赖图，确保执行顺序正确

**任务创建时机：**
- 复杂多步骤任务（3+ 步骤）
- 非平凡复杂任务
- Plan 模式下跟踪工作
- 用户显式请求待办列表

## 三、上下文管理机制

### 1. 三层上下文架构

> **来源说明：** 本节中 Memory Files 的机制来自官方系统提示声明；会话历史的存在已确认但压缩算法等细节未公开；即时上下文为作者根据行为观察归纳，非官方术语。

```
┌─────────────────────────────────────────────────────────┐
│ Layer 1: 持久记忆 (Memory Files) 【官方声明】            │
│ - 跨会话保持                                            │
│ - 项目约定、架构决策、用户偏好                           │
│ - 按主题组织，非时间顺序                                 │
│ - 文件: MEMORY.md (主), 其他主题文件                    │
│ - 声明位置: ~/.claude/projects/<project>/memory/        │
│ - MEMORY.md 自动加载，超过 200 行截断                    │
│ - 实际观察: 目录按需创建，首次写入时才生成                │
└─────────────────────────────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────┐
│ Layer 2: 会话历史 (Conversation History)                │
│ 【官方确认存在，压缩算法等细节未公开】                    │
│ - 当前对话的完整上下文                                   │
│ - 工具调用与结果                                         │
│ - 自动压缩机制                                           │
│ - 实际存储: ~/.claude/projects/<project>/<session>.jsonl │
│ - 格式: JSONL，每行一个消息对象                          │
│ - 本地存储为完整未压缩历史                               │
└─────────────────────────────────────────────────────────┘
                          ▼
┌─────────────────────────────────────────────────────────┐
│ Layer 3: 即时上下文 (Immediate Context) 【作者归纳】     │
│ - 当前任务焦点                                           │
│ - 最近读取的文件内容                                     │
│ - 活跃的 Agent 输出                                      │
│ - 注: 非官方术语，基于行为观察推断                        │
└─────────────────────────────────────────────────────────┘
```

### 2. 实际存储位置验证

**目录结构（实际观察）：**

```
~/.claude/
├── history.jsonl                    # 用户命令历史（跨所有项目）
├── projects/
│   └── <project-hash>/              # 项目名 hash 后的目录名
│       ├── <session-id>.jsonl       # 完整会话历史（未压缩）
│       └── memory/                  # Memory Files（按需创建）
├── tasks/                           # 后台任务状态
├── plans/                           # Plan 模式文件
├── file-history/                    # 文件编辑历史
├── shell-snapshots/                 # Shell 状态快照
├── cache/                           # 缓存
├── debug/                           # 调试日志
└── telemetry/                       # 遥测数据
```

**会话历史文件格式（JSONL）：**

```json
// 消息类型统计（当前会话示例）
{"type": "user", ...}           // 用户输入
{"type": "assistant", ...}      // 助手响应
{"type": "tool_use", ...}       // 工具调用
{"type": "tool_result", ...}    // 工具返回结果
{"type": "thinking", ...}       // 思考过程
{"type": "file-history-snapshot", ...}  // 文件状态快照
```

**Memory 目录状态：**
- 官方声明的路径在首次使用时才创建
- 目前项目未触发 memory 写入，目录不存在
- 属于可选功能，非强制启用

### 3. 自动压缩机制

> **官方声明：** "The system will automatically compress prior messages in your conversation as it approaches context limits."
>
> **实际观察：** 本地存储的 `<session>.jsonl` 文件保持完整未压缩历史，压缩可能发生在发送给 API 时。

**官方声明 vs 实际观察：**

| 方面 | 官方声明 | 实际观察 |
|------|----------|----------|
| 存在性 | 确认存在 | 存在（行为可见） |
| 触发时机 | 接近上下文窗口限制时 | 未公开 |
| 压缩算法 | 未公开 | 未公开 |
| 本地存储 | 未说明 | 完整未压缩 |
| 压缩环节 | 未说明 | 可能在 API 发送时 |

**推测的压缩策略（未官方确认）：**
```
原始对话 (100K tokens)
    │
    ├── 保留：关键决策、重要文件内容、任务状态
    │
    ├── 压缩：中间探索过程、重复信息
    │
    └── 丢弃：临时性、已解决的问题

压缩后对话 (30K tokens)
```

**设计意义：**
- 保持对话"无限"延续
- 关键信息不丢失
- 性能与记忆的平衡
- 减少 API token 消耗

**已知限制：**
- 压缩算法细节未公开，无法精确预测行为
- 本地历史完整保存，但 API 上下文会被压缩
- 压缩后可能丢失部分细节信息

### 4. Memory 文件设计原则

```yaml
保存内容:
  - 跨多次交互确认的稳定模式和约定
  - 关键架构决策和重要文件路径
  - 项目结构
  - 用户偏好（工作流、工具、沟通风格）
  - 反复出现问题的解决方案

不保存内容:
  - 会话特定的上下文（当前任务详情）
  - 可能不完整的信息
  - 与 CLAUDE.md 重复或矛盾的内容
  - 从单个文件推测的未验证结论
```

### 4. Plan 模式的阶段化设计

```
Phase 1: Initial Understanding
    │
    ├── Explore Agent 探索代码库
    ├── 理解用户意图
    └── 识别可复用组件
    │
    ▼
Phase 2: Design
    │
    ├── Plan Agent 设计方案
    ├── 权衡不同实现路径
    └── 输出详细步骤
    │
    ▼
Phase 3: Review
    │
    ├── 阅读关键文件
    ├── 确认与用户意图对齐
    └── 使用 AskUserQuestion 澄清
    │
    ▼
Phase 4: Final Plan
    │
    ├── 写入计划文件
    └── 包含验证方案
    │
    ▼
Phase 5: ExitPlanMode
    │
    └── 用户批准后执行
```

**设计原理：**
- 分离"思考"与"执行"
- 强制用户确认高风险操作
- 避免无效工作

## 四、工具链协同设计

### 1. 工具调用原则

```yaml
并行调用:
  - 多个工具无依赖关系时
  - 示例: 同时读取多个文件、并行启动多个 Agent

串行调用:
  - 后续调用依赖前面结果
  - 示例: 先搜索文件，再读取内容，然后编辑

禁止模式:
  - 禁止用 Bash 做 Read/Write/Grep 能做的事
  - 确保操作可审计、可回滚
```

### 2. 工具能力矩阵

| 工具 | 读 | 写 | 搜索 | 执行 | 隔离 |
|------|---|---|------|------|------|
| Read | ✅ | | | | |
| Write | | ✅ | | | |
| Edit | | ✅ | | | |
| Glob | | | ✅ | | |
| Grep | | | ✅ | | |
| Bash | | | | ✅ | |
| Agent | ✅ | ✅ | ✅ | ✅ | ✅ |

### 3. 专用工具优先原则

```
文件读取 → Read (不是 cat/head/tail)
文件编辑 → Edit (不是 sed/awk)
文件创建 → Write (不是 echo >)
文件搜索 → Glob (不是 find/ls)
内容搜索 → Grep (不是 grep/rg)
```

## 五、执行流程对比

### 传统大模型交互

```
用户输入 ──▶ 大模型生成 ──▶ 用户复制粘贴 ──▶ 手动测试
     ▲                                         │
     └───────────── 反馈错误 ←──────────────────┘
     (循环成本高，每次需重新描述上下文)
```

### Claude Code 交互

```
用户输入 ──▶ 理解意图 ──▶ 探索代码库 ──▶ 制定计划
                │                            │
                ▼                            ▼
           执行修改 ◀─── 多轮迭代 ◀─── 验证结果
                │
                ▼
           自动修复问题 ──▶ 完成
     (闭环自动执行，上下文持续累积)
```

## 六、安全与权限设计

### 1. 权限模式

```yaml
自动允许:
  - 读取文件
  - 搜索代码
  - 网络搜索

需要确认:
  - 写入文件
  - 执行命令
  - 网络请求
```

### 2. 风险操作识别

```yaml
高风险操作:
  - 删除文件/分支
  - Force push
  - 数据库操作
  - 修改 CI/CD 配置

处理策略:
  - 执行前明确告知用户
  - 默认询问确认
  - 用户可配置权限级别
```

### 3. 可逆性原则

```
可逆操作 (自由执行):
  - 编辑文件 (可 git restore)
  - 创建文件 (可删除)
  - 创建分支 (可删除)

不可逆操作 (需要确认):
  - 删除分支
  - Force push
  - 修改共享状态
```

## 七、设计哲学总结

| 原则 | 实现体现 |
|------|----------|
| **渐进式理解** | Explore → Plan → Execute 分阶段 |
| **最小惊讶** | 执行前确认，操作可逆 |
| **上下文守恒** | 自动压缩 + 持久记忆 |
| **并行优先** | Agent 可并行，工具可并发 |
| **验证闭环** | 执行后测试，错误自动修复 |
| **工具专用化** | 每个工具专注单一职责 |
| **可解释性** | 所有操作有明确描述 |

## 八、实际应用建议

### 何时使用 Plan 模式

- 新功能实现（涉及架构决策）
- 多文件修改（3+ 文件）
- 不确定用户意图（需要探索）
- 影响范围大的修改

### 何时直接执行

- 单行/几行修改
- 明确的 bug 修复
- 用户给出了具体指令
- 纯研究/探索任务

### 如何利用 Memory

1. 项目约定稳定后写入 MEMORY.md
2. 按主题创建专门文件（如 debugging.md）
3. 定期清理过时或错误的信息
4. 不要重复 CLAUDE.md 已有的内容
