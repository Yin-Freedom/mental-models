

### docx处理工具

使用skill-creator创建prd分析skill，发现读取docx的第一步LLM就重复造轮子使用python读取。

```
1. 解压 docx 文件
unzip -o "文档.docx" -d unpacked/
2. Python 解析 XML 并提取文本
3. 读取解析的文本 extracted_text.txt
```

存在问题

1. 原始文档结构丢失，中间处理过程不透明
2. 输入token更长

| 处理方式             | 词数量 | 影响                              |
| -------------------- | ------ | --------------------------------- |
| 原始docx文档         | 28422  | 需要数据清洗才能输入给LLM         |
| 解析的xml            | 516562 | 内容过多，需要通过脚本提取        |
| 解析的纯文本         | 25689  | 格式丢失                          |
| pandoc转换的markdown | 26284  | 人类可理解，LLM可理解的带格式文档 |

查看 `docx` 技能，对于读取docx描述过于简单，且没有使用如 、`IMPORTANT` 强调解析工具的优先级。

```
Reading Content
-------------------------------------------------------
# Text extraction with tracked changes
pandoc --track-changes=all document.docx -o output.md

# Raw XML access
python scripts/office/unpack.py document.docx unpacked/
```

对比python和pandoc进行docx处理后LLM处理情况：

| 方式             | 提取原理                      | 表格结构 | LLM处理难度 | 输出格式              | 适用场景           |
| ---------------- | ----------------------------- | -------- | ----------- | --------------------- | ------------------ |
| Python简单提取   | 只取`<w:t>`文本节点           | 丢失     | ⭐⭐⭐⭐⭐ 困难  | 纯文本流              | 快速全文检索       |
| Python结构化提取 | 按`<w:tbl>/<w:tr>/<w:tc>`解析 | 保留     | ⭐⭐⭐ 中等    | 二维数组              | 需编程处理表格数据 |
| Pandoc转换       | 解析docx完整结构              | 保留     | ⭐ 容易      | Grid Table / Markdown | 最佳方案           |

另外，对比Anthropic的官方技能，docx、pdf、excel、pptx的SKILL.md的组织结构并不一致。

结论：需要在system prompt（CLAUDE.md）明确指定处理某些文件的最佳工具。

###  提示语和模板

对于需求分析的整个任务，对每个阶段拆分prompt和模板。

阶段包括：

1. 文档结构分析
2. 模块功能性需求分析
3. 实体关系分析
4. 插件划分
5. 接口设计
6. 原型设计

prompt结构为：

```
# Phase 0: 文档结构分析Prompt
## 角色设定
## 任务描述
## 输入
## 输出格式
## 示例
```



存在两个问题：

1. 生成的实体、字段有遗漏，完整性检查不到70%
2. 在同一个prompt中的提示仍可能会被LLM忽略
